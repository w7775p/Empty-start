## 可比条件与差异

### 日志支持的共同条件

- Godot `4.7.2.stable.official.ed1daf0bf`，同一 Windows PC，D3D12 12_0 / Forward+，设备名为 AMD Radeon(TM) Graphics。
- `1920×1080` 逻辑视口、`1280×720` 客户区、窗口模式 `0`、VSync enabled、physics TPS `60`。
- 使用正式 Plan B Sandbox、稳定满员 96、人口稳定后预热 5 秒并采样约 20 秒。既有 PB-14 记录称前后使用相同 `--profiling --gpu-profile --print-fps` 参数；原始 stdout 没有回显完整启动命令。
- `formal_baseline_repeat_edcd8938.log` 和两个 post 日志均有 GPU PROFILE / Project FPS 输出；它们含同类引擎采样数据。

### 会影响解释的差异与缺口

- 普通战斗在自然推进，采样开始时阵营组成不同：优化前复测为 neutral/opponent `87/9`，`197ad3f6` 为 `85/11`，`6b384425` 为 `78/18`；采样结束时分别为 `84/12`、`75/21`、`52/44`。总人口相同，模拟阶段和画面构成未固定。
- 达到满员的启动时间也不同：日志记录的 `PB14_FULL_POPULATION` 分别约为 12.979 秒、18.420 秒、16.213 秒。满员后仍固定预热 5 秒；战斗在这段时间继续演进。
- `197ad3f6` 原始 profile marker 的 `commit` 字段是 probe 常量 `1ddd5b41`，没有记录真实 E 合并 SHA；候选来自文件名和当时的 E 任务记录。`6b384425` marker 同样带有 probe 常量 `1ddd5b41`，另有八位 `integration_candidate` 字段。证据记录不包含完整启动命令和每次运行时的完整 Git SHA。
- 日志可识别 GPU 名称，但没有 CPU 型号、显卡驱动版本、系统电源模式和 GPU 时钟信息；无法核对这些设备状态是否完全一致。
- 初次 Steam Editor 样本缺少上述 profile flags，已单独作为 unmatched supplemental evidence 保存，没有放入表格。
- `6b384425` 是零面积保护合入前的版本。保护代码在 `7336b74c` 中；尚无修复后窗口运行日志。

## 错误与告警

- 三份用于主要比较的 raw log 各有一条 `music_battle_t0` 缺失告警；均未出现 `SCRIPT ERROR`。
- `formal_postopt_6b384425_96.log` 在 profile marker 之间有一条渲染 ERROR：`Invalid polygon data, triangulation failed`，调用栈为 `_draw_group_bubble_tails` → `_draw_group_bubbles` → `_draw`。
- D 提交 `df90acbb` 与 A 提交 `6a3b2fea` 都在绘制前检查 `absf(target_tip.y - root.y) <= 0.001` 并跳过退化尾巴。A 合流的 headless UI smoke 通过，日志为 `tests/plan_b/evidence/pb12_14_d_ui_smoke_headless_polygon_guard_20261018.log`；headless 输出跳过 viewport 图片读取，因此不能证明 D3D12 窗口中的错误已经消失。

## 当前热点判断

- 当前证据里最大的 CPU monitor 是 `TIME_PROCESS`：`6b384425` 平均 `37.741 ms`；`TIME_PHYSICS_PROCESS` 平均 `25.278 ms`。两者均高于优化前同启动方式样本。wall frame mean 为 `183.919 ms`，其余帧耗时没有被本 probe 分解。
- 同一 `6b384425` 样本 draw calls 平均 `618.349`，约为优化前复测的 `1.95×`；GPU PROFILE 平均 `2.122 ms`，只比优化前复测高约 `0.211 ms`。这使 CPU 处理和绘制提交路径成为合理排查方向，仍无法单凭 GPU task time 排除驱动侧成本。
- `Performance.TIME_PROCESS` / `TIME_PHYSICS_PROCESS` 是引擎监视器。当前日志没有 `_draw_unit`、`_draw_group_bubbles`、`_draw_group_bubble_tails`、快照接入等方法的函数级耗时、调用次数或 inclusive/self time。最大具体函数为 **未知**。
- wall frame mean `183.919 ms` 与两个 process monitors 不能直接相加还原；当前证据没有覆盖每一帧其余开销的分解。

## Profile 探针自身开销

`formal_postopt_probe.gd` 只读正式模拟器的公开人口查询；采样期间每个渲染帧记录帧间隔、FPS、`TIME_PROCESS`、`TIME_PHYSICS_PROCESS`、draw calls，并读取一次 faction counts。它每秒打印 census，结束时复制和排序已收集的数值数组。源码注释注明它不复制棋子词条快照。

优化前和 post probe 的逐帧采样逻辑基本一致；post probe 还增加候选/人口参数解析和容量夹具分支。现有证据没有同版本、同场景、同战斗状态的“开启/关闭 probe 与 profiling”对照，故无法量化这些工作与 `--profiling`、GPU PROFILE、FPS 打印对帧率的影响。前后共同使用同类 probe/输出降低了部分系统性差异，运行时阵营状态与 probe 提交标记仍有上述缺口。

Godot 官方命令行参考将 `--profiling` 描述为在 script debugger 中启用 profiling，将 `--gpu-profile` 描述为显示耗时较大的 GPU rendering tasks；现有 stdout 只含引擎 monitors 和 GPU tasks，没有可读的 GDScript 函数明细。参考：[Godot command line reference](https://docs.godotengine.org/en/stable/tutorials/editor/command_line_tutorial.html)、[Godot CPU optimization](https://docs.godotengine.org/en/stable/tutorials/performance/cpu_optimization.html)。
