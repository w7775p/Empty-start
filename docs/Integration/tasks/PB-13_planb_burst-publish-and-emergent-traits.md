## 本次任务

### 一、确定性核心规则：一次发言产生一群棋子（P0）
1. 玩家从中央底部的预制话语候选中选定一句，**点击中央棋盘内任意有效坐标**即可发表；点击空地或已有棋子附近均可，不再要求点击现存中立观众。中央棋盘之外的主播栏/选句栏点击继续执行各自 UI 操作。
2. **按话语 `strength` 一次生成完整批次：1级 = 2颗、2级 = 4颗、3级 = 8颗。** 新棋子的 `team,word_id,word_order,battle_type,strength,traits` 与本次发表一致。每颗棋子拥有独立 `unit_id`、位置、速度、碰撞、寿命与后续可转化状态。
3. 批次在玩家点击坐标附近、约 0.5 秒内朝四周喷涌入场；视觉要明显、落点分散，进入场内后继续原有自主移动与碰撞。喷涌期间按实际出生棋子处理，不产生重复同位堆叠的多次感染判定。
4. 对手也通过同一个发表规则投放棋子：费米 AI 选择 `word_id` 和战场坐标，投放数量同样由其话语 strength 决定；对手原有反击技能单独运行。
5. **发表操作按整批计算一次**：原本的本场 `word_id` 一次性主动发表、发表冷却、唯一递增 `word_order`、对手/玩家对称的校验与成功提交继续生效。UI 选择、鼠标点击坐标本身不消耗冷却；**整批合法生成成功**才提交词耗与冷却并发出 `word_published` 事实。
6. 保持全场棋子数量上限，可从配置调整；为完整批次预留空间（优先调节中立持续出生节奏和自然离场）。容量不足时返回可解释的发表失败事实，不消耗词/冷却/顺序号；不以删掉已站队棋子的方式伪造腾位。真实生成量必须等于 2/4/8，不允许悄悄缩水后显示成功。

### 二、感染、传播和数值（P0）
1. 合法感染尝试的基础概率更新为：**strength 1 = 50%、strength 2 = 60%、strength 3 = 70%**，以感染方正在复读的话语强度判定。沿用可配置表，支持固定 seed 复核。
2. 原有三角克制决定敌我能否感染、同属性敌我只弹开、同阵营碰撞将较新的 `word_order` 连同完整话语快照传给较旧棋子、中立没有主动感染能力等规则继续有效。
3. 一次物理接触最多结算一次感染；成功后继承攻击者当前话语完整快照，更新阵营并发出 `unit_changed(reason=convert)`。新话接触传递发出 `unit_changed(reason=relay)`，不额外增加阵营人数。
4. PK 继续由 A 唯一按照 B 的真实三方人数和经过时间计算，原有 `k` 仅作为可调初值；生成的2/4/8颗真实棋子自然计入本方人数。调参验收时检查批量发言是否让 PK 过快触底或推满，优先使用参数修改使一局保持大约2～4分钟。

### 三、玩家方最小自动特性（P0，独立于基础投放接线）
1. **同一次发表的复读话语批次**（以 `word_order` / 发表事实识别）累计成功感染 **5** 个观众时，自动让该批仍在场的一颗本方棋子获得一次性随机特性，暂取 `split`（分裂）或 `reflect`（反弹）。此处采取“同批累计”而不是要求单个棋子独自感染5次，目的是让效果在真实局内能触发并直接回应玩家的那次发言。
2. 该发表批次最多触发一次奖励；分裂创建额外同话语棋子并遵守总人口上限，反弹在下一次合法受到克制感染时抵挡并击退攻击者一次。优先复用现有 B 的 `apply_counterattack_effect`、分裂/反弹概念与程序表现；所需的阈值、可抽取特性、每批上限以最少配置字段实现。
3. 以简短的程序化光圈、弹跳、复制/反弹动作表现特性，玩家能够直接看到棋子的进化和实际行为；真实次数/触发细节放 F3 Debug 或日志。对手原有技能保持其现有公开请求与前摇链路。
4. 此进化触发口径是本卡的**低成本首次实现选择**，与上面玩家已确定的2/4/8数量和50/60/70概率分开调节，避免特性成为批量发表的实现阻断点。

### 四、中央操作 UI 与视觉（P0）
1. 正式基准 1920×1080 保留左右主播区各 **448×1080**、顶部 PK 条 **1024×72**。中央剩余区域按 **棋盘1024×828 + 底部话语栏1024×180** 安排；战场点击响应只在棋盘内。
2. 候选使用已定的**抽取补位**规则，默认同时显示3句；每句可见原文、战斗类型、strength，支持鼠标和数字键选句。一句主动使用过后补新候选；冷却/不可发表有明显轻量反馈。
3. 点击棋盘任意位置时，从该处明显喷出本次话语对应的 2/4/8 颗角色棋子。玩家对本次发表的影响优先通过局部棋子爆发、阵营颜色变化、碰撞感染、分裂和反弹直接表现；正式战斗无需“本次新增N名信徒”一类统计型 HUD，真实数字留调试信息。
4. 使用刚交付的六种角色 `assets/ui/plan_b/units/*_unit.png`；棋子画面以头像+阵营/属性标记为主体，只有近期感染、指向/选中等局部事件显示短句；保持大批棋子时可读。
5. 普通 PK 阶段使用选话+落点投放，原有蓄力准星仅在到达100%后的六选一矛盾击破阶段启用；原矛盾内容（每关1真5假、10秒、一发最多命中一句）和后续结局流程继续接线。
6. 首关新手教学替换原有“点击一名中立观众”描述为“选话语→在棋盘点位置→看2/4/8棋子喷出→观察感染/反击→100%进入矛盾击破”；复用现有教学显示组件与 PB_04 数据来源。

### 五、模块交接与实施顺序
- **A（`scenes/plan_b/`, `systems/plan_b/battle/`, 正式流程接线）：** 将双方共用入口由 `publish_word(team,word_id,neutral_unit_id)` 迁为 `publish_word(team,word_id,spawn_position:Vector2)`（以实际工程已存在入口为准）；负责一次发表成功事务、冷却/去重/顺序号、PK、正式游戏战斗切换和局末过渡。
- **B（`systems/plan_b/simulation/`）：** 提供 `spawn_word_batch(spawn_position,team,word_definition,word_order,count)->bool` 或同等稳定公开入口，负责 2/4/8 个对象在场内创建、碰撞、感染概率、事实信号、同批传播计数、一次性特性实际效果及状态快照。
- **C（`systems/plan_b/content/`, `systems/plan_b/opponent/`, `data/plan_b/`）：** strength 数量/概率配置、对手目标位置与同一发表接口接线、原有反击请求协调；静态话语只读值快照仍为唯一文本来源。
- **D（`ui/plan_b/` 和接线所需 UI）：** 中央底部选句与棋盘点击位置、批次喷涌、阵营/属性可读性、已有 PNG 引用和短暂事件反馈；UI 只调用 A 的公开发表入口并消费 B 的事实快照。
- **E（`tests/plan_b/`）：** 用现有真 Godot 场景验收：strength 对应出生数、成功事务、概率、碰撞、对手等价投放、特性上限和直接可玩的战斗结果。
- 按 **B 批量能力 → A 提交入口 → C 对手投放与参数 → D 操作反馈 → E 实机核验** 依赖并发推进；子任务独立提交 commit，联调统一由 A 负责，保留现有公开 ID 与信号契约的最小改动。

### 六、本卡验收（真人实际游戏包）
- 选强度1话语并点击棋盘：喷出**2**颗；强度2喷出**4**颗；强度3喷出**8**颗。点击不同位置，对应批次从不同位置出现。对手使用同样的数量规则。
- 同一句一次发表只生成一次批次；点击 UI、冷却中、重复词、非法位置、容量不足时不误扣资源；96上限可配置且实机无爆量穿透。
- 固定条件下合法感染的强度概率配置已切换为 **50/60/70**；同类型敌对弹开，同阵营旧话接触改口、阵营转化继承快照、PK 变化均正确。
- 某次发表的传播累计成功感染达到5次，能看到一次性分裂或反弹实际生效，之后该批次不会重复刷特性；对手反击仍能使用。
- 1920×1080 中央选话区可点击，左右主播/PK保留，普通战斗隐藏旧蓄力输入；过场进入原六选一时恢复射击并正常收尾。
- 交付**直接可玩的更新包**、真实 Godot 运行截图或短录像、实际日志、引擎错误情况与要人工验收的手感。程序冒烟只是验收的一部分。

## 执行要求（对应任务卡模板14项）

### 1. 先检查当前项目状态
核对当前 branch/worktree、未提交改动、最新有效 PR；阅读 `project.godot` 里的 autoload、插件、Input Map 与渲染设置；通过 Godot-MCP-Native 核实真实 scene/node、信号与 Resource。以最新可运行代码作为开发基线。

### 2. 严格控制任务范围
集中完成批量投放、强度感染率、一次性自动特性、中央输入布局及相关正式接线；其他系统仅修改直接依赖。已有内容继续复用。

### 3. 保持最小必要复杂度
将出生批次和特性判断放在既有棋子拥有者，已存在的公开接口最小改签名；用配置、简单状态与事件表达当前规则。

### 4. 组合优于继承
由场景、普通节点、已有 Resource、信号和现有功能组件组合棋子、技能和 UI；单个行为内聚到其数据拥有者。

### 5. 保持场景边界
A 组合场景并协调生命周期；B 唯一维护棋子事实；C 提供词定义和 AI 决策；D 只做展示和用户输入；E 验证接口。跨模块通信采用稳定公开方法/信号/ID。

### 6. 区分场景、逻辑和数据
静态表进入 `data/plan_b/` 或现有数据配置；战斗现场对象在 B；PK 与发表事务在 A；纯运算和配置继续使用项目现有适当数据类型。

### 7. 新增实现前按顺序检查
先复用仓库已完成的批量实体、碰撞、分裂/反弹、Tween 动画与原始美术；不足处使用 Godot 原生 Node/Resource/API 补齐。

### 8. Godot API 不允许猜
对本引擎版本不确定的 API 通过 `godot_mcp` 的 class/method/property/signal 查询核实并记录关键依据。

### 9. 使用 Godot-MCP-Native 检查真实工程
实际检查输入节点、战场坐标变换、碰撞区域、渲染顺序、资源导入、事件信号和运行时节点数量；使用真实 Godot 项目编辑与运行检查。

### 10. 自动化与额外保障机制
利用现有测试/调试日志核验批次、概率与事件；真实玩法、画面密度和手感由真人验收；提交最少必要的自动校验材料。

### 11. 避免脆弱的 Godot 依赖
保持场景依赖由稳定导出引用、节点注入和信号连接表达；一次发表的所有者明确为 A，棋子运行事实明确为 B。

### 12. 修改现有场景时尊重现有结构
先确认父/子场景实例、owner、UID、Resource 和现有连接，再对中央交互部分进行最小定向修改；左右主播、原结局和故事组件复用。

### 13. 验证实际 Godot 行为
至少完成 GDScript 解析、场景/资源加载、玩家/对手实际批次投放、感染与自动特性、PK 结算、矛盾阶段接线的运行验收；保留真实截图/录像。

### 14. 完成前检查
