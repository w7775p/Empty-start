## 已经实现的功能
- `INT-02` 已建立 1920×1080 三列战斗界面：左 448、中 1024、右 448；中央顶部状态区 72px。
- `scenes/sandbox/sandbox.tscn` 当前中央 `BarrageArea` 为相对中央区的 `(0,72,1024,760)`，`OracleCandidateDisplay` 同范围，底部 `ChargeFeedback` 占 `(0,832,1024,248)`。
- `scenes/sandbox/sandbox_battle_hud.gd` 目前从 `ChargeState` 和 `ChargeProgress` 读取占位显示控件，`refresh_attack(progress,phase)` 接收实际攻击状态。
- `data/stage_layout/stage_layout_profile.tres` 仍保存旧的弹幕区高度与底部交互区高度。
- 攻击输入、蓄力进度、鼠标准心、暂停菜单分别已有对应系统与场景。

## 本次任务
**把中央底部旧交互栏改为弹幕战斗空间，并将鼠标左键、ESC 的纯操作 ICON 竖排显示在中央战斗场左下角。**

### 触发条件
玩家进入 Sandbox 普通战斗界面、矛盾击破界面或相关中央战斗显示界面时。

### 预期行为
1. **中央区域尺寸**：设计基准保持 1920×1080；左主播区宽 448px、中央战斗区宽 1024px、右主播区宽 448px。中央顶部 `TopBattleStatus` 仍占高度 72px，显示现有 PK 条、Tier 与阶段文字。
2. **弹幕区域全高**：把中央顶部以下的全部空间交给 `BarrageArea`，新的中央局部矩形为 `(0,72,1024,1008)`；以全画面坐标计为 `(448,72,1024,1008)`。普通弹幕、复读、特殊话语的生成/移动/瞄准区域覆盖这一整块空间。
3. **旧底部交互栏整理**：释放 `ChargeFeedback` 原有的 248px 布局空间，移除旧进度条占位、`ChargeState` 文字和 `ControlsHint` 的画面占位；将现有 `SandboxBattleHud.refresh_attack(progress,phase)` 与 `reset_for_attempt()` 的显示引用调整为新界面可用的入口，继续接收真实攻击状态。
4. **操作 ICON 浮层**：在中央战斗区左下角固定一列操作提示，按从上到下排列：
   - **鼠标左键 ICON**：提示蓄力与松开发射。
   - **ESC 按键 ICON**：提示暂停。
   两项都以单独的按键图标呈现。ICON 贴靠中央区左下边缘，建议每项约 40～48px、相隔约 12～16px、距左/下边缘各约 24～32px；具体最终值按实际界面协调。
5. **ICON 与弹幕共用画面**：操作 ICON 作为固定位置的 HUD 浮层展示；它们覆盖在全高弹幕场的角落，弹幕保持在浮层后方持续出现和移动。ICON 承担视觉提示，鼠标输入继续由现有攻击和暂停系统处理；图标显示控件允许准心和射击输入正常穿过。
6. **中央其他显示区域同步**：`OracleCandidateDisplay` 等与弹幕场共用中央活动区域的现有场景和命中展示位置，随新的全高尺寸对齐，继续正确显示与选择相应目标。
7. **布局数据同步**：更新 `stage_layout_profile.tres` 与必要的 `StageLayoutProfile` 字段，使编辑器中打开 `sandbox.tscn` 时看到的矩形与运行时一致；按现有 `BattleHud` 统一缩放适配 PC 窗口、全屏和 Android 屏幕。
8. **蓄力反馈美术接入**：保留现有攻击蓄力进度与阶段状态的程序提供能力，供另行交付的正式美术蓄力反馈使用；本卡完成中央战斗区布局和两枚操作 ICON 的程序承载。

### 验收条件
- 1920×1080 基准下，中央 `TopBattleStatus` 为 1024×72；`BarrageArea` 从 y=72 延伸到中央区底边，尺寸为 1024×1008。
- 中央区域从 PK 条下沿到屏幕底部均可出现弹幕，准心能瞄准并命中靠近底部的目标。
- 左下角能看到上方鼠标左键 ICON 和下方 ESC ICON；两枚 ICON 竖向排列，跟随窗口尺寸正确缩放，显示期间弹幕仍覆盖整个战斗区域。
- 旧底部蓄力条占位、蓄力文字与多行操作说明已从布局中释放；顶部 PK、Tier、阶段提示维持正确显示。
- 鼠标按住蓄力、松开发射、ESC 暂停、返回游戏继续操作正常；`refresh_attack` 的蓄力状态继续可供美术接入读取。
- Paradox/神谕候选在调整后的中央区域内完整显示，准心位置、目标实际位置与命中判定一致。
- Godot 编辑器的 Sandbox Scene 预览与真实运行的布局一致；分别检查 1920×1080、1280×720、960×540 画面和一次全屏/窗口切换，输出对应实际画面与日志。
- Godot Output / Debugger 没有新增关联报错。

## 执行要求
### 1. 先检查当前项目状态
- 确认当前 branch、未提交修改、已有实现；核对 `project.godot` 的版本、Autoload、插件、Input Map、渲染器。
- 检查相关 `.tscn`、`.gd`、`.tres`、`.res`、节点职责、信号与资源依赖；以真实工程和最新已合并代码为准。

### 2. 严格控制任务范围
- 本张卡只完成“本次任务”所定义的功能和验收；发现关联问题在日志中说明，按任务依赖单独处理。

### 3. 保持最小必要复杂度
- 依赖方向清晰、代码高内聚；拆分场景或脚本以独立变化、生命周期、状态、流程或复用等实际需求为依据。

### 4. 组合优于继承
- 根据现有结构，优先采用子节点、子场景、Resource、signal、公开方法组合行为；仅在明确的 is-a 关系中使用业务继承。

### 5. 保持场景边界
- 父场景协调生命周期与组合，子模块维护自身状态；跨系统通过公开接口、稳定 ID、signal 或数据对象协作。

### 6. 区分场景、逻辑和数据
- Node/Scene 承载场景行为，Resource 承载静态配置，普通脚本对象承载纯逻辑；新增 Autoload 需有真实跨场景生命周期需求。

### 7. 新增实现前按顺序检查
- 依次检查仓库已有实现、Godot 原生 API、已安装 addon/plugin 和语言标准能力；需要新实现时采用满足本卡的最小方案。

### 8. Godot API 不允许猜
- 对 Node、属性、方法、signal、枚举和版本行为存疑时，使用 `godot_mcp` 查询对应 Godot 官方文档并核实后实现。

### 9. 使用 Godot-MCP-Native 检查真实工程
- 涉及场景树、节点、Inspector、连接、运行状态与画面时优先使用 `Godot-MCP-Native` 实际检查；MCP 不可用时记录原因和可替代的 CLI / 人工验证。

### 10. 自动化与额外保障机制
- 优先复用既有测试入口；仅针对稳定可复现的规则补充必要自动化。视觉、动画、交互与手感以真实运行及人工验收为依据。
- hash、baseline、gate、contract 或额外框架必须有明确且可复现的失败依据。

### 11. 避免脆弱的 Godot 依赖
- 检查跨模块内部 NodePath、固定父级层级、节点名业务身份、跨场景 Node 引用和多余 Singleton 耦合；使用稳定公开接口协作。

### 12. 修改现有场景时尊重现有结构
- 修改前核对场景实例、继承、owner、Resource 内嵌/外部关系及信号连接来源，保留有效 UID、节点路径和现有引用。

### 13. 验证实际 Godot 行为
