# INT-05 Windows UI／全屏与分辨率验收

## 开始前先阅读以下文档
- AGENTS.md、known_traps.md、project.godot
- docs/Original/任务卡模板.md
- docs/Integration/README.md 与相关完成日志
- 当前相关 Scene、Resource、代码与前置任务卡

## 目标
以最新 main 的 Windows 可运行版本，在不同窗口尺寸和显示比例下验收各页面 UI、全屏切换、弹幕与鼠标准心的显示和交互。

## 已经实现的功能
- 当前项目已有主菜单、开局、战斗、休息和结局页面；以现有集成测试和最新完成日志判定已接通范围。

## 本次任务

### 测试基准
- 引擎：Godot 4.7.2；设计参考：1920×1080（16:9）。
- 记录当前 main commit SHA、Windows 版本、显示器原生分辨率、系统 DPI 缩放比例、运行方式、窗口客户区实际尺寸及 Godot Viewport 尺寸。
- 以真实运行窗口、全屏和场景切换结果为验收依据；截图与日志对应具体测试环境。
- 核对当前 `project.godot` 的 `window/stretch/mode="canvas_items"`、`window/stretch/aspect="expand"`，以及 `scenes/sandbox/sandbox.tscn` 中固定设计宽度：左 448px、中央 1024px、右 448px。

### 测试点

### 01 全屏与窗口
1. FS-01：首次启动进入主菜单；记录窗口模式、实际画面尺寸和显示位置。
2. FS-02：在设置中开启全屏、返回窗口模式；确认画面铺设、按钮位置、实际鼠标点击范围。
3. FS-03：连续切换全屏与窗口 5 次；确认每次切换后的布局、交互和稳定性。
4. FS-04：窗口模式拖动四边与四角，缩小后重新放大；检查各 UI 的缩放、排列与恢复。
5. FS-05：全屏运行时 Alt+Tab 切出再切回；确认画面显示、焦点、鼠标和交互。
6. FS-06：在战斗暂停界面的设置中切换全屏；确认暂停层、设置层和返回流程。
7. FS-07：全屏状态依次进入开局、房间、战斗、Rest、Ending；确认跨场景窗口状态和布局。
8. FS-08：修改全屏设置、退出并重启；确认配置保存与恢复。
9. FS-09：显示缩放率 100%／125%／150% 及多显示器场景，有相应测试设备时记录运行结果。

### 02 页面 UI
1. UI-01 主菜单：标题、开始游戏、设置、退出四处完整显示并可点击。
2. UI-02 设置：四条音量滑块、全屏开关、恢复默认、返回；在 960×540 下完整操作。
3. UI-03 身份开局三页：身份选项、主播名、粉丝团名、文本输入及每一步切换；使用较长合法名称检查文字适配。
4. UI-04 开局主角房间：房间背景、身份装饰、主播信息、「开始直播」按钮。
5. UI-05 战斗左列：玩家主播名、立绘占位、直播数据 ICON 与数字。
6. UI-06 战斗中央：PK 条、Tier／阶段状态、全高弹幕区、准心、左下角鼠标左键与 ESC 竖排 ICON；按 INT-06 检查美术蓄力反馈的程序入口。
7. UI-07 战斗右列：对手名称、立绘占位、直播数据 ICON 与数字。
8. UI-08 战斗失败覆盖层：失败说明及重新开始按钮。
9. UI-09 暂停与设置覆盖层：继续游戏、设置、返回主菜单、重新开始；检查按钮命中和覆盖层输入。
10. UI-10 矛盾／神谕候选：句子完整显示、选择范围与实际命中判定。
11. UI-11 战后 Rest：结果文本、直播数据、奖励、历史圣典、败者卡和继续按钮；检查历史内容展示与返回。
12. UI-12 神降临：话语扩散、锁句、全屏强调及动画结束后的画面恢复。
13. UI-13 Ending：标题、圣典、空收藏、较长经文与判词；检查长内容滚动和窗口缩放后的布局。

### 03 坐标、裁切和布局边界
1. IN-01：分别在 1920×1080、1280×720、960×540 的战斗场景，检查左／中／右三列完整显示、比例、重叠和画面边界。
2. IN-02：将鼠标放在中央弹幕区四角、中心及可命中的弹幕上；确认准心图形中心、鼠标事件位置和实际攻击命中一致。
3. IN-03：全屏与窗口互切后立即蓄力发射；验证准心位置、蓄力反馈和命中结果。
4. IN-04：在窗口拖动缩放后再次瞄准、蓄力和发射；验证新的 Viewport／Canvas 坐标映射。
5. IN-05：在不同宽高比下测试左右主播区、中央战斗区、弹幕边界和背景填充；记录具体裁切或留白区域。
6. IN-06：在小窗口内打开设置、暂停、失败、Rest、历史收藏等面板；验证标题、正文、操作按钮完整可见及正确响应。
7. IN-07：在 Ending 放入长文本与多条历史内容，滚动到末尾，改变窗口尺寸后继续滚动；验证内容位置与滚动区域。
8. IN-08：在各关键界面执行窗口最小化／恢复、窗口最大化／还原；验证 UI 与点击区域恢复。

### 验收条件
- P0 分辨率 R01～R04 的主菜单、三步开局、开局房间、战斗、设置、暂停、Rest、Ending 均有完整验收记录。
- 主操作按钮完整可见、文字可辨认，弹窗和滚动内容可正常访问。
- 全屏、窗口切换及连续缩放后的鼠标点击、准心绘制、蓄力和命中位置一致。
- 三列 HUD、直播数据、PK／Tier、全高弹幕区、左下操作 ICON 与正式美术蓄力反馈具有明确的显示范围；发现的布局异常有可复现记录。
- 每项测试标注 PASS／FAIL／未测，汇总 P0／P1／P2 缺陷和对应设备、尺寸、截图证据。

## 执行要求
### 1. 先检查当前项目状态
- 确认当前 branch、未提交修改、已有实现；核对 `project.godot` 的版本、Autoload、插件、Input Map、渲染器。
- 检查相关 `.tscn`、`.gd`、`.tres`、`.res`、节点职责、信号与资源依赖；以真实工程和最新已合并代码为准。

### 2. 严格控制任务范围
- 本张卡只完成“本次任务”所定义的功能和验收；发现关联问题在日志中说明，按任务依赖单独处理。

### 3. 保持最小必要复杂度
- 依赖方向清晰、代码高内聚；拆分场景或脚本以独立变化、生命周期、状态、流程或复用等实际需求为依据。

### 4. 组合优于继承
- 根据现有结构，优先采用子节点、子场景、Resource、signal、公开方法组合行为；仅在明确的 is-a 关系中使用业务继承。

### 5. 保持场景边界
- 父场景协调生命周期与组合，子模块维护自身状态；跨系统通过公开接口、稳定 ID、signal 或数据对象协作。

### 6. 区分场景、逻辑和数据
- Node/Scene 承载场景行为，Resource 承载静态配置，普通脚本对象承载纯逻辑；新增 Autoload 需有真实跨场景生命周期需求。

### 7. 新增实现前按顺序检查
- 依次检查仓库已有实现、Godot 原生 API、已安装 addon/plugin 和语言标准能力；需要新实现时采用满足本卡的最小方案。

### 8. Godot API 不允许猜
- 对 Node、属性、方法、signal、枚举和版本行为存疑时，使用 `godot_mcp` 查询对应 Godot 官方文档并核实后实现。

### 9. 使用 Godot-MCP-Native 检查真实工程
- 涉及场景树、节点、Inspector、连接、运行状态与画面时优先使用 `Godot-MCP-Native` 实际检查；MCP 不可用时记录原因和可替代的 CLI / 人工验证。

### 10. 自动化与额外保障机制
- 优先复用既有测试入口；仅针对稳定可复现的规则补充必要自动化。视觉、动画、交互与手感以真实运行及人工验收为依据。
- hash、baseline、gate、contract 或额外框架必须有明确且可复现的失败依据。

### 11. 避免脆弱的 Godot 依赖
- 检查跨模块内部 NodePath、固定父级层级、节点名业务身份、跨场景 Node 引用和多余 Singleton 耦合；使用稳定公开接口协作。

### 12. 修改现有场景时尊重现有结构
- 修改前核对场景实例、继承、owner、Resource 内嵌/外部关系及信号连接来源，保留有效 UID、节点路径和现有引用。

### 13. 验证实际 Godot 行为
- 完成后检查脚本解析、Scene/Resource 加载、相关场景运行、Output/Debugger，以及本卡“验收条件”。
- 涉及 UI、动画、运动、输入或其他视觉表现时实际运行并保存必要截图；Headless 结果按其覆盖范围说明。

### 14. 完成前检查
- 复查范围、复用、复杂度、Scene/Resource 引用与信号方向、死代码和测试投入；确认本卡实际通过后提交。
- 每张开发任务使用独立 branch，按 `AGENTS.md` 提交对应系统的完成日志；合并前同步最新目标分支重新验证。
